# screen-retina

Локальное многослойное восприятие экрана для LLM на Windows.

Когда модели скармливают скриншоты, она дорого восстанавливает то, что компьютер и так знает: каждое окно, кнопка и строка текста были структурированными данными, прежде чем стать пикселями. screen-retina сначала читает эту структуру, к OCR и vision-модели обращается только там, где структуры нет, и отдаёт модели короткие текстовые события вместо картинок.

Используется как «сетчатка» в computer-use агенте [AI Vision](https://github.com/LDRION/ai-vision). Python, около 1 800 строк, 24 теста.

## Слои

| Слой | Что делает | Цена |
|---|---|---|
| 0a пиксели | Снимает все мониторы, находит изменившиеся клетки 32 px, постоянно меняющиеся помечает как движение («горячие») | бесплатно, ~30 мс на кадр |
| 0b структура | Дерево UI Automation для окон, у которых изменились пиксели (один кэшированный межпроцессный вызов) | бесплатно, 20–150 мс на окно |
| 1a OCR | Встроенный OCR Windows — только на изменившихся клетках, текст которых UI Automation ещё не дал | бесплатно, 15–40 мс на полосу текста |
| 1b глаза | Локальная vision-модель через Ollama — только когда начинается движение, меняется сцена в движущейся области, появляется крупная новая картинка или по команде `look` | локальные токены |
| 2 мозг | Локальная модель Ollama, которая держит журнал событий в своём KV-кэше | локальные токены, только новые |

Восприятие работает как видеокодек: ключевой кадр (сводка окна), когда фокус переходит в другое окно или когда дельта вышла бы длиннее сводки, иначе — только дельты. Таймеры и счётчики, которые меняются постоянно, глушатся после трёх изменений. Набор текста прореживается до одного обновления в секунду и передаёт только добавленный текст.

### Формат событий

```
[02:50:10] window: chrome.exe «Search - Google Chrome» [left monitor]
combo «Search» = «screen retina»
btn «Search»
[02:50:14] ~ combo «Search» += « ollama»
[02:50:15] focus → link «github.com»
[02:50:20] @explorer.exe ~ btn «Clock 2:50» → «Clock 2:51»
[02:50:31] ▶ motion -1920,0 1920x1080 [left monitor] (50% of screen) in group «YouTube player»
[02:50:33] seen motion -1920,0 1920x1080 [left monitor]: gameplay clip with a hero fighting in a forest
```

`+` появилось, `-` исчезло, `~` изменилось, `+=` дописан текст, `@proc` — фоновое окно, `«...»` без роли — текст OCR.

## Замеры на моей машине

RTX 4060 8 ГБ, i5-12400F, два монитора 1920×1080, Ollama 0.30.8.

- **Задержка восприятия** (кадр снят → событие готово): p50 ~250–350 мс, p95 ~450–650 мс, плюс до 100 мс ожидания следующего кадра при 10 fps.
- **Токены.** Первый взгляд на все открытые окна стоит примерно как один скриншот (2–4 тыс. токенов); дальше неподвижный экран не стоит ничего. По сравнению со скриншотом раз в секунду: в **38 раз** меньше токенов за 30 с на одном мониторе, в **96 раз** — за 41 с на двух. Разрыв растёт со временем и сокращается, пока экран занят (набор текста, прокрутка).
- **Мозг** (`qwen3-vl:4b-instruct` или `qwen2.5:7b`, контекст 8 тыс.): первый токен ответа за ~0,2–0,3 с, короткие ответы за 0,7–1,8 с. Вопрос вычисляет только ~60–200 новых токенов, остальной журнал уже в KV-кэше. `qwen2.5:3b` быстрый, но часто неверно читает журнал.
- **Глаза.** В Ollama 0.30.8 vision-энкодер qwen3-vl работает на CPU (`clip_ctx: CLIP using CPU backend` в логе сервера): ~17 с и ~1 100 токенов на взгляд. Структура и OCR от этого не зависят.

Ollama сообщает `prompt_eval_count` как полную длину промпта даже при попадании в кэш, поэтому инструмент считает вычисленные токены как прирост промпта между вызовами.

## Запуск

**Лаунчер:** двойной клик по `Screen Retina.bat` (или `.venv\Scripts\python -m retina ui`). Выберите модель Ollama, включите или выключите глаза, нажмите «Старт»; окно показывает экономию, задержку и ленту событий вживую, в нём можно задать вопрос или попросить посмотреть. Окно лаунчера исключено из восприятия, поэтому модель не читает собственную ленту. Закрытие окна останавливает наблюдение.

**Командная строка:**

```
python -m venv .venv && .venv\Scripts\pip install -r requirements.txt
ollama pull qwen3-vl:4b-instruct          # тег qwen3-vl:4b без -instruct всегда «думает» и отвечает пусто

.venv\Scripts\python -m retina watch --model qwen3-vl:4b-instruct --eyes same
.venv\Scripts\python -m retina ask "Что я сейчас делаю?"
.venv\Scripts\python -m retina look                    # описать окно на переднем плане
.venv\Scripts\python -m retina look --rect -1920 0 1920 1080
.venv\Scripts\python -m retina state                   # вся текущая картина текстом
```

Параметры `watch`: `--fps`, `--quiet` (не печатать события), `--no-ocr`, `--lang ru|en-US`, `--ctx`, `--port`. Локальный API на 127.0.0.1:8765: `GET /state /events /stats`, `POST /ask {"q": ...}`, `POST /look {"rect": [x, y, w, h]}`.

### API для курсора

Та же живая картина, но с координатами — для агентов, которые двигают мышь. Модель здесь не участвует: поиск — это нормализация текста и нечёткое сравнение по тому, что восприятие уже держит.

| Вызов | Что возвращает |
|---|---|
| `GET /elements?scope=fg\|all&area=x,y,w,h&hidden=1&refresh=1` | все цели для клика: роль, имя, значение, состояние, экранные `rect` и `center`, `source` (`uia`/`ocr`), окно, `visible` |
| `GET /find?q=Отправить&role=btn&limit=5` | лучшие цели по подписи с ранжированием; `ambiguous: true`, если две одинаково хороши |
| `GET /events?since=42` | события после номера 42 в виде `[{seq, kind, text}]` и `last` — что изменилось на экране после действия |
| `POST /exclude {"prefixes": ["AI Vision"]}` | перестать воспринимать окна, чей заголовок так начинается (окно журнала самого агента) |
| `GET /settled?quiet=300&timeout=5000&expect=1&scope=fg` | ждёт, пока пиксели (окна на переднем плане или `area`) простоят `quiet` мс и изменившиеся окна будут перечитаны; `changed` — изменилось ли что-то после запроса |

Цели для клика хранятся отдельно от журнала событий: журнал называет каждую подпись один раз, а три кнопки «Удалить» остаются тремя целями. Строки OCR несут рамки слов, поэтому совпадение внутри склеенной строки («Mail Maps Market») возвращает рамку именно слова. Интерактивные роли важнее простого текста, окно на переднем плане важнее остальных, элементы, закрытые другим окном, отбрасываются. Если совпадений нет, дерево доступности окна на переднем плане перечитывается один раз (Chrome и Electron строят его лениво).

Строки OCR режутся по широким промежуткам на сегменты-подписи; совпадение внутри длинного сегмента — это текст (сообщение в чате, где упомянуто «Отправить»), а не элемент управления, и оно получает низкий балл. `exclude=title` (можно повторять) пропускает окна, в заголовке которых есть эта строка: окно журнала агента показывает ровно те подписи, которые он ищет.

Тесты: `.venv\Scripts\pip install -r requirements-dev.txt && .venv\Scripts\python -m pytest`.

## Приватность

Всё работает локально. Журналы событий пишутся в `data/` (в git не попадает) и содержат всё, что было на экране. Поля паролей маскируются. API слушает только 127.0.0.1.

## Известные ограничения

- Программы без дерева UI Automation (игры, некоторые лаунчеры) переходят на OCR и глаза.
- Chrome и Electron строят дерево доступности только после первого запроса, поэтому самый первый снимок такого окна может быть бедным.
- Если запустить `watch` в видимом терминале, его вывод попадает на экран; фильтр эха игнорирует его в окне-хозяине, а `--quiet` убирает совсем.
